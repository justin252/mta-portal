# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

CircuitPython app for an Adafruit MatrixPortal M4 LED matrix. Auto-cycles between L train arrivals (Graham Av), G train arrivals (Metropolitan Av), and current weather. Fetches train data from `wheresthefuckingtrain.com` API and weather from NWS forecast API. Buttons jump to L (UP) or G (DOWN) screens. Long press toggles full-screen train pixel art.

## Platform

- **Hardware**: Adafruit MatrixPortal M4 + 64x32 RGB LED matrix
- **Runtime**: CircuitPython (not CPython — no pip, no stdlib, limited memory)
- **No build step** — code runs directly on the microcontroller

## Development

**Deploy**: `cp code.py diag.py logic.py weather.py *.bmp /Volumes/CIRCUITPY/ && cp -r fonts /Volumes/CIRCUITPY/`. Train bitmap (`train.bmp`) is generated by `generate_train_bitmap.py`. Board auto-runs `code.py` on save (auto-reload).

**Debug**: Connect serial console (e.g. `screen /dev/tty.usbmodem* 115200` or Mu editor) to see `print()` output and errors.

**WiFi config**: Board reads `settings.toml` on CIRCUITPY drive for `CIRCUITPY_WIFI_SSID` and `CIRCUITPY_WIFI_PASSWORD`. This file is on-device only, not in the repo.

**Libraries**: Adafruit CircuitPython Bundle libs required on device in `/lib`: `adafruit_matrixportal`, `adafruit_display_text`, `adafruit_bitmap_font`, `adafruit_datetime`, `adafruit_debouncer`. Install by copying `.mpy` files from the bundle.

**Simulate display** (desktop, requires Pillow):
```bash
python3 simulate_display.py                          # L train, placeholder times
python3 simulate_display.py --line G                 # G train
python3 simulate_display.py --north 3,8,14 --south 1,5,12
python3 simulate_display.py --weather --condition sun --temp 72  # weather screen
```
Outputs `simulated_display.png` (640x320, 10x scale). Parses the same BDF fonts and BMP bitmaps used on-device. Weather conditions: sun, cloud, rain, snow, storm, fog. `--led` shows only the colors the LEDs can produce.

## Architecture

- `code.py` — hardware-dependent main loop: fetch → parse → display. Runs on-device only.
- `logic.py` — pure functions (`get_arrival_in_minutes_from_now`, `filter_arrivals`, `format_arrival_triple`). Works on both CircuitPython and desktop.
- `weather.py` — pure functions for NWS weather parsing (`parse_nws_forecast`, `map_condition`, `format_temperature`). Works on both CircuitPython and desktop.
- `simulate_display.py` — PIL-based display simulator, pixel-exact against board captures (`test_fixtures/device/`). Positions come from `layout.py`.
- `layout.py` — screen layout (positions, fonts, colors, stations) for the simulator, mirroring `code.py`.
- `diag.py` — board side of verification: `s` on the USB console dumps the framebuffer and the state that produced it.
- `tools/portal.py` — host side: `verify` captures the board's screen and diffs it against the simulator.
- `generate_weather_bitmaps.py` — generates 6 weather icon BMPs (sun/cloud/rain/snow/storm/fog) for the LED matrix.
- Screen cycling: L train → G train → weather → L train → ... every 10s. Buttons jump to L/G immediately; cycling resumes.
- Long press (1s) either button → toggle full-screen train pixel art. Short press in train art → return to cycling.
- Polls train API every 30s (both L and G), weather API every 5min
- Resets microcontroller after `ERROR_RESET_THRESHOLD` (3) consecutive train API failures
- Weather errors are non-fatal — shows stale data or skips weather screen
- Structured serial logging: `[OK]`, `[ERR]`, `[WEATHER]`, `[RECONNECT]`, `[RESET]`, `[BTN]` prefixes

## Testing

**Every display change is checked against what the board actually renders**, not just the simulator:

```bash
make setup    # once: .venv with pillow, pytest, pyserial
make test     # desktop: simulator vs board captures, layout rules (run from the repo root)
make verify   # board on USB: capture the current screen, diff against the simulator; exit 1 on mismatch
```

`verify` writes `out/device_x10.png`, `out/sim_x10.png` and `out/diff.png`; read them when it fails.

**Reference images come from the board**: `test_fixtures/device/*.txt` are framebuffer dumps captured with `tools/portal.py shot` (only `[FB]` lines). `test_simulate_display.py` requires the simulator to reproduce each one pixel for pixel. After an intentional layout change: deploy, capture each screen, replace the fixture.

**The formulas** (each pinned by a test):
- Text placement (`simulate_display.render_text`, same as `adafruit_display_text.Label`): glyph top = `y - bbx_h - bbx_yoff + font_ascent // 2`; x advances by DWIDTH. Fits iff the last glyph's ink ends at x ≤ 63 (`test_layout.py`).
- LED color: RGB888 → RGB565 (truncate), then the Protomatter driver keeps the top `BIT_DEPTH` (2) bits per channel: `level = c8 >> 6`. Channels below 64 are off.
- Framebuffer dump: RGB565 little-endian, one hex row per `[FB]` line.

**Serial monitoring**: `screen /dev/tty.usbmodem* 115200` — watch structured logs during operation.

**Fault injection checklist** (for network changes):
1. Disable router WiFi 60s → verify `[RECONNECT]` logs, board recovers
2. Disable WiFi 5+ min → verify `[RESET]` after threshold, board reboots and recovers
3. Block API endpoint → verify `[ERR]` logs distinct from WiFi errors

## CircuitPython Constraints

- No threading, async limited — single main loop only
- Limited RAM (~200KB) — avoid large data structures, prefer `.mpy` compiled libs
- `adafruit_datetime` is a subset of Python's `datetime` (no full `timezone` support)
- Network calls can block and raise `RuntimeError` on connectivity issues
